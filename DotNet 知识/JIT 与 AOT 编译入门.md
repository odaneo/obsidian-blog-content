
C#源代码通常先被编译成IL，也就是中间语言。CPU最终执行的是机器码，因此还需要一次从IL到机器码的转换。

JIT与AOT最主要的区别，是这次转换发生在什么时候。

## JIT在运行时编译

JIT是即时编译。应用运行时，运行时环境把需要执行的IL编译成当前平台的机器码。

```text
C#源代码 → IL → 运行时JIT编译 → 机器码
```

它不表示“每调用一次方法，就从头编译一次”。生成的代码可以在当前进程中继续使用，运行时也可能根据执行情况进一步优化。

同一份IL可以由不同平台的.NET运行时执行，但JIT生成的机器码仍然针对具体的操作系统和CPU架构。[Microsoft：托管执行过程](https://learn.microsoft.com/en-us/dotnet/standard/managed-execution-process)

JIT的一个代价是启动和首次执行某些代码时需要编译。对于长期运行的服务，这部分成本可以被较长的运行时间摊薄。

## Native AOT在发布时编译

AOT是预先编译。在.NET中谈到发布为独立本机程序，通常指Native AOT。

```text
C#源代码 → IL → 发布时AOT编译 → 面向目标平台的本机程序
```

Native AOT程序在运行时不使用JIT，通常能改善启动速度和内存占用。它会包含运行所需的运行时组件，目标机器不需要另行安装.NET运行时，但仍然需要满足对应平台的系统依赖。

发布结果针对具体的目标环境。Windows x64与Linux x64通常要分别发布。

它也有兼容性要求，例如不支持任意的动态程序集加载和运行时代码生成，并且需要配合裁剪。使用反射的代码和第三方库，需要检查AOT兼容性及发布警告。[Microsoft：Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/index)

## 两种方式怎样比较

| 对比项 | JIT | Native AOT |
| --- | --- | --- |
| 机器码生成时机 | 运行时 | 发布时 |
| 启动成本 | 可能包含即时编译 | 通常减少了即时编译成本 |
| 运行时动态能力 | 通常更灵活 | 受AOT及裁剪规则约束 |
| 部署目标 | 根据发布方式与运行时决定 | 明确针对目标平台和架构 |
| 稳态性能 | 可利用运行时优化 | 需要按实际负载测量 |
| 产物体积 | 受部署方式影响 | 同样受依赖、泛型及裁剪结果影响 |

“AOT一定运行得更快”或者“AOT一定占更多空间”，都过于绝对。比较体积时，还要区分依赖机器上已有运行时的发布方式，与把运行时一起带上的自包含发布方式。

## ReadyToRun是另一种选择

ReadyToRun也会提前生成部分本机代码，但通常同时保留IL，运行时仍可能使用JIT。它主要减少启动阶段的编译工作，与不使用JIT的Native AOT不是同一种发布模式。[Microsoft：ReadyToRun](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run)

## 按项目约束选择

| 项目情况 | 可以优先评估的方向 |
| --- | --- |
| 依赖较多动态功能的常规服务 | 先使用JIT，再根据启动指标评估ReadyToRun |
| 冷启动频繁的小型服务或命令行工具 | 检查依赖兼容性后评估Native AOT |
| WinForms、WPF等桌面项目 | 以具体框架及版本的支持情况为准 |
| iOS等对运行时代码生成有限制的平台 | 遵循对应.NET工作负载的AOT发布要求 |

实际选择还需要看应用框架、部署平台和依赖库。启动耗时、峰值内存、吞吐量与构建时间，都应在目标环境里测量。
