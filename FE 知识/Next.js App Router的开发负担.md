我喜欢React里直接的开发体验：写组件、管理状态，再把功能组合起来。但是到了Next.js App Router，同一个功能往往还要先回答几个问题：放服务端还是客户端，能不能用这个Hook，页面到底会不会缓存。框架提供了更多能力，也让日常开发多了不少判断。这甚至没有Next.js Pages Router好用，直观，让日常的开发多了很多心智负担。

## 组件需要先分两类

App Router的页面和布局默认是服务端组件。需要点击事件、`useState`、`useEffect`或浏览器API时，再声明客户端组件：

```tsx
"use client";
```

麻烦在于，这个声明还会影响该文件导入的组件和依赖，它们会进入客户端代码范围。原本顺手的组件组合，开始需要考虑运行位置。

不过，通过`children`传进来的服务端组件，可以继续在服务端渲染。不能把这条规则理解成“客户端父组件下面的一切都会变成客户端组件”。[组件边界说明](https://nextjs.org/docs/app/getting-started/server-and-client-components)

Redux等状态管理工具也需要放在客户端组件中。通常会单独封装一个Providers组件，再由服务端布局使用：

```tsx
<Providers>
  {children}
</Providers>
```

这能解决问题，却也增加了一层结构。对于交互和共享状态很多的页面，我会明显感觉到这种额外成本。

## 客户端组件也能预渲染

“客户端组件”这个名字很容易让人误会，以为加上`"use client"`，首屏就只能等浏览器执行JS后才出现。

在默认的首次页面加载中，Next.js也会为客户端组件生成初始HTML。浏览器接收后，再通过Hydration让按钮、输入框等具备交互能力。

两者的区别可以这样看：

| 类型    | 首次加载时的作用               | 浏览器是否需要组件代码 | 是否需要水合 |
| ----- | ---------------------- | ----------- | ------ |
| 服务端组件 | 在服务端生成渲染结果，参与页面输出      | 不需要下载该组件代码  | 不需要    |
| 客户端组件 | 也能参与HTML预渲染，之后在浏览器处理交互 | 需要          | 需要     |
水合可以理解为：浏览器给已经显示出来的HTML接上React的状态和事件逻辑。这个逻辑跟以往的Nextjs没有区别。

而`useEffect`会在浏览器中运行，写在里面的请求不会为服务端首屏提供数据。间接影响SEO水平。

这些概念各有用途，但命名并没有把差别直接说明白，团队需要额外花时间对齐理解。

## 体积和安全确实有收益

假设文章页面用了一个很大的Markdown处理库。把它留在服务端组件中，浏览器只接收渲染结果，就不用下载这个库。

这说的是这部分代码不会进入浏览器，并不代表整个网站的JS体积为零。客户端组件和框架仍然需要自己的代码。

服务端组件也方便读取数据库和服务端密钥。但查询结果只要渲染进页面，或作为属性传给客户端，就可能被用户看到。查询权限和返回字段仍要控制。[数据安全说明](https://nextjs.org/docs/app/guides/data-security)

我认可这些收益。只是当应用本身交互很多时，需要反复拆分组件，节省下来的下载体积是否值得这些开发成本，就要看具体项目了。

## 缓存需要理解更多规则

博客文章通常希望生成一次，多次复用，过一段时间再更新。到了App Router，开发者还要区分动态路径、动态渲染、数据缓存和页面缓存。

例如，`/posts/[slug]`只是路径参数化，并不意味着页面一定不能缓存。页面是否读取登录Cookie、怎样获取数据、项目启用了哪套缓存机制，都会影响结果。

在未启用Cache Components、使用传统ISR且支持该功能的部署环境中，公开文章页可以采用这样的配置片段：

```typescript
export const revalidate = 3600;

export async function generateStaticParams() {
  return [];
}
```

这里让文章路径按访问需求生成，并在达到一小时后由后续请求触发重新验证。它不是每小时自动执行一次的定时任务。[路径生成说明](https://nextjs.org/docs/app/api-reference/functions/generate-static-params)

这段也不是适用于所有版本和配置的通用写法。启用Cache Components后，需要按对应规则处理缓存。

让我疲惫的正是这些前提。看起来相同的页面需求，可能因为版本和配置不同，要采用不同的实现方式。

## 对于开发者友好也很重要

内容展示多、交互少的页面，可以把正文留在服务端，把搜索框和按钮等交互部分单独交给客户端。这样想法确实很不错。

但对于状态复杂的管理后台，我更在意写代码是否顺手、排查问题是否直接。App Router的收益需要和这些成本一起衡量。

我尊重Next.js团队的选择，也理解它想解决的问题。只是对我而言，如今需要记住的边界和规则越来越多，曾经那种简单好用的感觉正在变淡。
