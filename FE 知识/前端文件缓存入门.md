打开网页时，浏览器会下载HTML、JS、CSS和图片。下次再访问，如果文件没变，就可以复用已经下载的内容。

缓存要解决两个问题：没变的文件少下载，更新后的文件能及时用上。

## 强缓存直接用本地文件

服务器可以通过响应头告诉浏览器，这个文件多久以内可以直接复用：

```http
Cache-Control: public, max-age=31536000, immutable
```

- `public`：浏览器和CDN等共享缓存都可以保存。
- `max-age=31536000`：有效期为一年。
- `immutable`：这个地址的内容在有效期内不会改变，无需反复确认。

命中有效缓存时，浏览器直接用本地文件，省去一次网络请求。这通常叫强缓存。[Cache-Control说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

这里的一年是缓存有效期，浏览器仍可能因为空间不足等原因清理文件。

## 文件更新就换名字

假设第一次发布的文件叫：

```text
app.a1b2.js
```

修改代码后，webpack可以根据文件内容生成新的名字：

```text
app.c3d4.js
```

这就是`contenthash`的用途。新HTML引用新文件名，浏览器就会下载新文件；没有变化的资源继续使用缓存。

因此，长时间缓存适合带内容哈希的资源。像`app.js`这样一直使用同一个名字、内容却经常变化的文件，不能直接照搬这个策略。

## 协商缓存先问服务器

缓存过期后，如果保存了校验信息，浏览器可以先问服务器：“我手里的文件还是最新版吗？”

常用的校验方式有两种：

| 服务器返回 | 浏览器下次请求携带 | 比较什么 |
| --- | --- | --- |
| ETag | If-None-Match | 文件的版本标识 |
| Last-Modified | If-Modified-Since | 文件的修改时间 |

文件没变，服务器返回`304 Not Modified`，不再传输文件正文，浏览器继续使用原来的副本。文件变了，就返回`200 OK`和新内容。[ETag说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/ETag)

协商缓存仍会发送请求，只是文件没变时可以少传数据。

ETag的生成方式由服务器决定，不一定是文件内容的哈希。Nginx直接提供静态文件时默认支持ETag；代理后端响应时，通常由后端提供校验信息。[Nginx说明](https://nginx.org/en/docs/http/ngx_http_core_module.html#etag)

## HTML需要及时检查更新

HTML是页面入口，里面写着要加载哪些JS和CSS。如果HTML长期停留在旧版，浏览器就不知道已经有了新文件名。

公开页面的HTML可以设置：

```http
Cache-Control: no-cache
```

`no-cache`允许保存缓存，但复用前需要向服务器确认；`no-store`才是要求不要保存响应。[HTTP缓存说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

一次发布的过程可以这样理解：

```text
更新HTML中的资源地址
→ 浏览器检查HTML是否变化
→ 拿到新HTML
→ 下载改名后的资源
→ 继续复用没有变化的资源
```

## Nginx配置示例

假设这是一个公开的静态网站，`/assets/`目录里只放带内容哈希的资源：

```nginx
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

location ~* \.html$ {
    add_header Cache-Control "no-cache";
}
```

这两段放在已有的`server`配置中，文件目录和路由仍按项目设置。不要把会原地覆盖的图片或用户上传文件混进长期缓存目录。

如果网站更新后仍显示旧页面，可以先在浏览器的Network面板检查HTML的缓存头和实际返回内容，再检查CDN或Service Worker是否也保存了旧版本。手动刷新能恢复，只能说明缓存值得排查，不能单凭这一点确定是哪一层的问题。
