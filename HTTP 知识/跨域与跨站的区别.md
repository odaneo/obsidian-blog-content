跨域和跨站使用不同的判断标准。理解它们之前，先拆开一个URL。

## URL由什么组成

以`https://api.example.com:8443/orders?status=paid#details`为例：

| 部分 | 含义 | 示例 |
| --- | --- | --- |
| Scheme | 协议方案 | `https` |
| Host | 主机名 | `api.example.com` |
| Port | 端口 | `8443` |
| Path | 资源路径 | `/orders` |
| Query | 查询参数 | `status=paid` |
| Fragment | 页面内片段 | `details` |

片段标识不随HTTP请求发送给服务器。

## 跨域看源

同源要求协议、主机和有效端口都相同。这里常说的“跨域”，指跨源。

网页脚本读取跨源响应时，通常需要服务器通过CORS授权。有些跨源请求可以发送，但脚本不能读取响应；需要预检的请求，则先检查预检结果。[MDN的CORS说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

## 跨站看站点

在SameSite语境中，同站按协议和可注册域判断，端口不参与。可注册域依据公共后缀列表确定，例如`example.co.uk`。[MDN的站点说明](https://developer.mozilla.org/en-US/docs/Glossary/Site)

以`https://www.example.com`为基准：

| 目标地址 | 是否跨域 | 是否跨站 |
| --- | --- | --- |
| `https://api.example.com` | 是，主机不同 | 否 |
| `https://www.example.com:8443` | 是，端口不同 | 否 |
| `http://www.example.com` | 是，协议不同 | 是 |
| `https://other.com` | 是，主机不同 | 是 |

## Cookie怎样控制发送范围

服务器通过Set-Cookie设置Cookie及其属性：

| 属性 | 作用 |
| --- | --- |
| name=value | Cookie名称和值 |
| Domain | 省略时只属于当前主机；设置父域可覆盖其子域，不能指定无关域或公共后缀 |
| Path | 限定匹配路径，`/app`可匹配`/app/user`，但不匹配`/apple` |
| Max-Age / Expires | 设置存活秒数或到期时间；同时设置时Max-Age优先 |
| HttpOnly | 阻止JavaScript直接读取Cookie，符合条件的请求仍可自动携带 |
| Secure | 通常只通过HTTPS发送，本地localhost有例外 |
| SameSite | 限制跨站请求携带Cookie的条件 |

未设置Max-Age和Expires时，Cookie属于会话Cookie；浏览器的会话恢复功能可能将它一并恢复。[Set-Cookie属性说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)

## SameSite与CSRF

| 值 | 跨站请求中的行为 |
| --- | --- |
| Strict | 不携带 |
| Lax | 顶层页面的安全方法导航通常携带，例如点击外链发起GET；跨站POST、图片和iframe请求通常不带 |
| None | 允许跨站携带，但必须同时设置Secure |

跨源Fetch还受凭据配置影响，跨站Cookie也受浏览器的第三方Cookie策略限制。

CSRF利用浏览器自动携带登录凭据，诱使服务器执行用户没有主动发起的操作。SameSite可以减少部分攻击机会，服务端仍应结合CSRF Token等机制验证请求。[CSRF说明](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/CSRF)
