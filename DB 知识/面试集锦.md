本文统一按PostgreSQL回答。索引示例默认讨论普通B-tree索引；涉及其他索引类型或版本差异时，会单独说明。

### Q1：SQL 性能优化方式有哪些？

**A：**

先定位慢在哪里，再决定改SQL、索引还是表结构。

1. 看执行计划。用`EXPLAIN (ANALYZE, BUFFERS)`检查实际耗时、估计与实际行数、循环次数，以及缓存命中和读取情况。
2. 按查询设计索引。结合筛选、连接和排序条件考虑单列或联合索引；需要时使用表达式索引、部分索引等。索引也有写入和维护成本。
3. 减少不必要的工作。只查需要的列，避免重复查询；深分页可以考虑基于稳定排序键的游标分页。
4. 维护统计信息和表。`ANALYZE`更新统计信息，`VACUUM`清理可回收的旧行版本；关注autovacuum是否正常工作。
5. 再考虑更大的调整。按数据量与访问方式评估分区、物化视图、缓存或只读副本。

PostgreSQL执行计划常见这些节点：

| 节点 | 含义 |
| --- | --- |
| `Seq Scan` | 顺序扫描表 |
| `Index Scan` | 通过索引定位，再访问表数据 |
| `Index Only Scan` | 尝试从索引取出所需数据 |
| `Bitmap Index Scan`、`Bitmap Heap Scan` | 先收集行位置，再访问表 |
| `Sort`、`Hash Join`等 | 排序、连接等处理 |

例如：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name FROM users WHERE name = 'Tom';
```

`ANALYZE`选项会实际执行SQL，修改数据的语句也会产生相应效果。只想查看计划、不执行时，使用普通`EXPLAIN`。PostgreSQL没有MySQL式的`type/key/Extra`执行计划列。[执行计划](https://www.postgresql.org/docs/18/using-explain.html)

`Seq Scan`不一定差，索引扫描也不一定快。`EXISTS`不总比`IN`快，子查询也不必一律改成JOIN，应该结合实际数据比较。[VACUUM与ANALYZE](https://www.postgresql.org/docs/18/routine-vacuuming.html)

**面试速答：** 先用执行计划定位耗时，再检查索引、SQL写法、统计信息和表维护，最后评估分区、缓存等方案。

### Q2：20 张表联表查询如何优化？

**A：**

先确认这20张表是否都需要参与，再区分是执行慢，还是规划连接顺序本身就很慢。

- 检查结果是否被放大。一对多连接、漏写连接条件，都可能让中间结果远大于预期。
- 提前表达有效筛选条件。减少参与计算的数据，但不能认为SQL写在前面的表就一定先执行。
- 检查连接键、索引和统计信息。类型应尽量匹配；估计行数偏差很大时，先考虑`ANALYZE`，必要时评估扩展统计信息。
- 看实际连接算法。PostgreSQL会选择`Nested Loop`、`Hash Join`或`Merge Join`，不能简单套用“小表驱动大表”。
- 必要时拆分工作。中间结果可以存入临时表并执行`ANALYZE`；报表场景可评估物化视图。拆成多次查询也要考虑网络开销和数据一致性。

大量表连接还涉及GEQO遗传查询优化器。是否启用取决于查询形态和参数，`geqo_threshold`默认是12。20张表联查可能触发它，但不宜直接把关闭GEQO当成优化方案。[查询规划参数](https://www.postgresql.org/docs/18/runtime-config-query.html)

另外，子查询或`WITH`不保证先生成一份独立中间结果。PostgreSQL可能将它合并到外层查询；`MATERIALIZED`可以影响这个行为，但也可能阻碍条件下推。[WITH查询](https://www.postgresql.org/docs/18/queries-with.html)

**面试速答：** 先查连接关系、数据量和行数估计，再看连接算法与规划耗时；确有需要时再用临时表、物化视图或拆查询。

### Q3：索引的原理是什么？

**A：**

索引是帮助数据库快速定位数据的辅助结构。PostgreSQL默认使用B-tree，适合等值、范围和排序查询，但不是所有索引都采用B-tree。

其他常见类型包括：Hash用于等值比较，GIN用于数组、部分JSONB查询和全文检索等，GiST、SP-GiST支持空间等可扩展搜索，BRIN适合数据与物理位置相关的大表。具体能力取决于数据类型和操作符类。[索引类型](https://www.postgresql.org/docs/18/indexes-types.html)

#### 表数据与索引分开存放

PostgreSQL普通表的数据放在heap中，普通B-tree叶子条目保存索引键和指向表行的物理位置。普通索引扫描找到位置后，通常还要访问heap。

主键通常会创建唯一B-tree索引，但表数据不会因此始终按主键排列。其他索引也不是统一保存主键值再去查主键索引，不能套用InnoDB的存储模型。

`CLUSTER`可以按某个索引重排表，但后续写入不会自动维持这个顺序。[CLUSTER](https://www.postgresql.org/docs/18/sql-cluster.html)

#### 覆盖索引不保证零回表

可以用`INCLUDE`把查询需要的额外列放进索引：

```sql
CREATE INDEX idx_users_name_include_id
ON users (name) INCLUDE (id);

SELECT id, name
FROM users
WHERE name = 'Tom';
```

查询所需列都在索引里，才有机会采用`Index Only Scan`。是否仍访问heap，还要看可见性映射，因为PostgreSQL需要确认行版本对当前事务是否可见。执行计划中的`Heap Fetches`可以帮助判断。[Index-Only Scan](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

**面试速答：** PostgreSQL默认用B-tree辅助定位数据，索引与heap分开存放；覆盖所需列后可能使用Index Only Scan，但可见性检查仍可能访问表。

### Q4：如何优化 SQL 中的 `a or b` 或者 `in/not in` 等关键字性能？

**A：**

#### 1. OR不必一律拆开

两边有合适索引时，PostgreSQL可能通过`BitmapOr`合并扫描结果，再用`Bitmap Heap Scan`读取表数据。是否更快取决于命中行数和成本。[合并多个索引](https://www.postgresql.org/docs/18/indexes-bitmap-scans.html)

```sql
SELECT id, a, b
FROM t
WHERE a = 1 OR b = 2;
```

直接拆成下面两段`UNION ALL`，同时满足条件的行就会出现两次。若确实要改写，可以让分支互斥：

```sql
SELECT id, a, b FROM t WHERE a = 1
UNION ALL
SELECT id, a, b FROM t
WHERE b = 2 AND a IS DISTINCT FROM 1;
```

`IS DISTINCT FROM`也考虑了a为NULL的情况。这个改写只保证筛选语义，是否值得采用仍需看计划；改成`UNION`又会引入去重，不能当作通用优化。

#### 2. IN可以正常使用

```sql
SELECT id, a FROM t WHERE a IN (1, 2, 3);
```

小列表且存在合适索引时，`IN`通常没有问题。大量值可以评估临时表或其他集合输入方式。

`IN (SELECT ...)`也不是天然低效，优化器可能将它处理为半连接。判断`IN`和`EXISTS`，应看相关性、数据分布与执行计划。

#### 3. NOT IN先检查NULL语义

如果子查询中出现NULL，`NOT IN`对未匹配值的判断可能变成UNKNOWN，导致这些行不被返回。

业务需要表达“另一张表不存在匹配记录”时，可以直接使用：

```sql
SELECT t.id
FROM t
WHERE NOT EXISTS (
    SELECT 1
    FROM t2
    WHERE t2.id = t.id
);
```

`NOT EXISTS`和`NOT IN`对NULL的处理不同，不能不核对数据约束就认定二者等价。`NOT EXISTS`也可能采用反连接或内部索引扫描，不是“否定条件一定不走索引”。[子查询表达式](https://www.postgresql.org/docs/18/functions-subquery.html)

**面试速答：** OR可能使用BitmapOr，拆UNION ALL要避免重复；IN和EXISTS看计划比较，NOT IN则先检查NULL语义。

### Q5：什么是死锁？什么是事务？

**A：**

#### 事务

事务把多条操作放进一个工作单元，用`COMMIT`提交，用`ROLLBACK`撤销。

```sql
BEGIN;

UPDATE tasks SET status = 'running' WHERE id = 1;
UPDATE tasks SET status = 'running' WHERE id = 2;

COMMIT;
-- 如果选择取消这次事务，则执行ROLLBACK，而不是COMMIT。
```

ACID可以这样理解：

- 原子性：事务中的修改整体提交或撤销。
- 一致性：依靠约束和正确的业务逻辑，使数据保持合法状态。
- 隔离性：按隔离级别限制并发事务之间的影响，并非完全互不干扰。
- 持久性：通过WAL等机制支持已提交数据的崩溃恢复，具体保证受提交和存储配置影响。

PostgreSQL默认使用Read Committed。普通查询按语句取得快照，可以看到语句开始前其他事务已提交的数据，也能看到本事务此前的修改。

MVCC能减少普通读写之间的阻塞，但写写冲突、显式锁和DDL仍可能造成等待。[事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)

#### 死锁

死锁是事务互相等待对方持有的锁，形成循环：

- 事务A先锁住行1，再等行2。
- 事务B先锁住行2，再等行1。
- 两边都无法继续。

PostgreSQL检测到死锁后，会中止其中一个事务，让其他事务有机会继续。死锁错误的SQLSTATE是`40P01`；序列化失败则通常是`40001`。[锁与死锁](https://www.postgresql.org/docs/18/explicit-locking.html)，[错误代码](https://www.postgresql.org/docs/18/errcodes-appendix.html)

减少死锁的常见做法是统一访问和加锁顺序、缩短事务、避免在事务中等待用户或网络。遇到可重试错误时，应用需要重试完整事务，而不是只重放最后一条SQL。

**面试速答：** 事务负责一组操作的提交与撤销；PostgreSQL默认Read Committed，并用MVCC管理并发。死锁是循环等锁，数据库会中止一个事务，应用按需要重试。

### Q：什么情况下索引会失效？

**A：**

在PostgreSQL里，通常说的是“这次查询没有采用预期的索引”，不一定是索引本身失效。要区分条件无法匹配索引，和优化器认为别的计划更便宜。

#### 1. 查询表达式与索引不匹配

普通列索引不一定能直接支持函数或运算后的条件：

```sql
-- 假设create_time是timestamp without time zone，且有普通列索引。
SELECT id FROM orders
WHERE create_time::date = DATE '2024-01-01';

-- 用时间范围表达同一天，便于利用原列索引。
SELECT id FROM orders
WHERE create_time >= TIMESTAMP '2024-01-01 00:00:00'
  AND create_time <  TIMESTAMP '2024-01-02 00:00:00';
```

如果字段是`timestamptz`，需要按业务时区确定日期边界，不能不加区分地照搬。

函数也不意味着永远不能走索引。例如，可以为大小写无关查询建立表达式索引：

```sql
CREATE INDEX idx_users_lower_name ON users (lower(name));
SELECT id FROM users WHERE lower(name) = 'tom';
```

索引表达式还需要满足不可变性等要求。[表达式索引](https://www.postgresql.org/docs/18/indexes-expressional.html)

#### 2. 类型或操作符不匹配

PostgreSQL不会像某些数据库那样，任意把字符串和数字隐式转换后比较。例如，phone是text时，直接写`phone = 13800000000`通常会报操作符不匹配。

显式转换索引列，也可能让普通列索引无法匹配：

```sql
-- 对phone做转换；非数字内容还可能让查询报错。
SELECT id FROM users WHERE phone::bigint = 13800000000;

-- 如果phone按文本存储，就用文本条件比较。
SELECT id FROM users WHERE phone = '13800000000';
```

JOIN也应检查连接键类型。不是任何类型差异都会让索引不能用，重点是实际使用的转换、操作符和索引是否匹配。

#### 3. 模糊匹配与索引类型不合适

`LIKE '%postgres%'`通常无法通过普通B-tree高效缩小扫描范围。`LIKE 'post%'`则可能使用B-tree，但也受排序规则和操作符类影响。

例如，对text列可以考虑：

```sql
CREATE INDEX idx_users_name_pattern ON users (name text_pattern_ops);
SELECT id FROM users WHERE name LIKE 'post%';
```

varchar列有对应的`varchar_pattern_ops`。[操作符类](https://www.postgresql.org/docs/18/indexes-opclass.html)

包含匹配可以评估`pg_trgm`扩展的GIN或GiST索引：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING GIN (name gin_trgm_ops);
SELECT id FROM users WHERE name LIKE '%postgres%';
```

搜索词太短、无法提取有效trigram时，效果可能有限。全文检索主要针对词项，不是任意子串搜索的通用替代。[pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html)

#### 4. 联合索引的前导列约束不足

对于`(a, b, c)`的B-tree索引，前导列的等值条件、随后首个范围条件，通常对缩小扫描区间最重要。

```sql
CREATE INDEX idx_t_a_b_c ON t (a, b, c);

SELECT id FROM t WHERE b = 2;
SELECT id FROM t WHERE a = 1 AND b > 10 AND c = 3;
```

第一条没有约束a，可能需要扫描较大范围，但不能断言完全无法使用索引。第二条中的c仍可以参与索引内检查，并非“范围后面的列全部失效”。

PostgreSQL 18还支持B-tree skip scan，在前导列不同值较少等条件下，可以利用后续列条件进行跳跃查找；是否采用由成本决定。[联合索引](https://www.postgresql.org/docs/18/indexes-multicolumn.html)

#### 5. OR或否定条件的访问成本高

OR的一部分没有合适索引，或者整体命中很多行时，优化器可能选择顺序扫描。但OR也可能使用BitmapOr，`NOT EXISTS`也可能通过反连接等方式高效执行。

这些关键字本身不是索引失效开关，改写方法和NULL语义见Q4。

#### 6. 排序方式与索引顺序不匹配

对于`ORDER BY`，列顺序、方向、NULL位置和排序规则都会影响B-tree能否直接提供所需顺序。不匹配时，计划可能出现`Sort`；已有部分顺序时，也可能采用`Incremental Sort`。

`GROUP BY`可能采用排序聚合，也可能采用`HashAggregate`，不要求一律按索引列顺序书写，也不保证输出已经排序。PostgreSQL这里不使用MySQL的`filesort`术语。[索引与排序](https://www.postgresql.org/docs/18/indexes-ordering.html)

#### 7. 顺序扫描更便宜或统计信息不准确

小表、查询返回大量行、索引列重复值很多时，顺序扫描可能更划算。没有“返回超过80%就一定不用索引”这样的固定阈值。

估计行数和实际行数相差很大时，应检查统计信息，必要时执行：

```sql
ANALYZE orders;
```

还要结合数据分布、表膨胀和实际I/O判断，不能只看有没有使用索引。[ANALYZE](https://www.postgresql.org/docs/18/sql-analyze.html)

#### 8. SELECT *增加取数成本

`SELECT *`不会直接让索引失效，但可能让查询需要读取更多heap数据，失去Index Only Scan的机会，进而改变成本选择。

查询只需索引中的列时也不保证完全不访问heap，还要考虑可见性映射，见Q3。

**面试速答：** PostgreSQL不走预期索引，常见原因是表达式、类型、操作符或排序规则不匹配，也可能是联合索引扫描范围太大、统计信息不准，或顺序扫描本来更便宜。不能把函数、OR、NOT EXISTS或最左前缀背成绝对规则；最终结合`EXPLAIN (ANALYZE, BUFFERS)`判断。

### Q：DbContext的并发限制和最佳实践是什么？

**A：**

`DbContext`是EF Core在应用中创建的数据库访问对象，负责查询、实体跟踪和保存修改。它内部维护共享状态，不支持同一个实例同时执行多个数据库操作。

PostgreSQL可以并发处理查询，但这不表示应用里的同一个DbContext对象也支持并发。即使两个操作都是只读查询，也不能在同一个实例上重叠执行。[并发限制](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/#avoiding-dbcontext-threading-issues)

#### Scope与实例共享

`AddDbContext<InventoryDbContext>`默认注册为Scoped。同一次HTTP请求中，两个Service分别通过构造函数注入它，会拿到同一个实例；另一个请求通常使用另一个实例。

可以注入多次，也可以查询多次。限制针对同一个实例上的操作重叠，Scope本身不限制并发。

| 使用方式 | 是否支持 |
| --- | --- |
| 两个Service持有同一个DbContext，先后查询 | 支持 |
| 同一个DbContext，库存查询没结束就开始查幂等记录 | 不支持 |
| 不同请求各用自己的DbContext，同时查询 | 支持 |
| 同一请求内，通过工厂创建两个独立DbContext，同时查询 | 支持 |

#### Controller示例

美国库存服务检查某个SKU的库存，再查询Checkout幂等记录。以下沿用Scoped注册，假设库存表和幂等记录表已经映射：

```csharp
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;

[ApiController]
[Route("api/checkout")]
public class CheckoutController : ControllerBase
{
    private readonly InventoryDbContext _db;

    public CheckoutController(InventoryDbContext db)
    {
        _db = db;
    }

    [HttpGet("check")]
    public async Task<IActionResult> Check(
        string sku,
        int warehouseId,
        Guid requestId,
        CancellationToken token)
    {
        // 等库存查询完成，再使用同一个DbContext执行下一条查询
        var stock = await _db.Stocks
            .AsNoTracking()
            .FirstOrDefaultAsync(
                s => s.Sku == sku && s.WarehouseId == warehouseId,
                token);

        var history = await _db.IdempotencyRecords
            .AsNoTracking()
            .FirstOrDefaultAsync(
                r => r.RequestId == requestId,
                token);

        return Ok(new { stock, history });
    }
}
```

每条操作立即`await`，等待完成后再执行下一条。等待数据库时不会一直占着线程；查询完成后，即使后续代码换了线程，也可以继续使用这个DbContext。

下面的写法会让两个查询重叠使用同一个实例，不受支持：

```csharp
var stockTask = _db.Stocks.ToListAsync(token);
var historyTask = _db.IdempotencyRecords.ToListAsync(token);

await Task.WhenAll(stockTask, historyTask);
```

`Task.WhenAll`不会让查询排队，`Task.Run`也不能解决共享DbContext的问题。确实需要并发时，每个并发操作使用独立实例，例如通过`IDbContextFactory<InventoryDbContext>`创建。[DbContext工厂](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/#use-a-dbcontext-factory)
