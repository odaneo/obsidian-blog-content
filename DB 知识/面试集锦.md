
### Q1：SQL 性能优化方式有哪些？

**A：**  
主要从这几方面：

1. **索引**
   - 建合适索引
   - 避免索引失效：不要在索引列上做函数、运算、隐式转换。

2. **查询语句**
   - 避免 `select *`，只查需要的列。
   - 用 `exists` 替代 `in`，用 `union all` 替代 `or`。
   - 分页优化，避免深分页。
   - 减少子查询，尽量 join。

3. **表结构**
   - 合适字段类型。
   - 适当冗余。
   - 分区、分表、分库。

4. **执行计划**
   - 用 `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`。
   - 关注全表扫描、文件排序、临时表。

5. **架构**
   - 缓存、读写分离、异步、批量处理。

**例子：**

```sql
-- 索引失效
select * from orders where date(create_time) = '2024-01-01';

-- 优化后
select * from orders
where create_time >= '2024-01-01'
  and create_time < '2024-01-02';
```

### Q2：20 张表联表查询如何优化？

**A：**  
先问一句：**真的必须 20 张表一起 join 吗？**  
很多场景可以拆成多次查询，应用层组装。

优化思路：

1. **减少 join 数量**
   - 核心表先过滤，得到小结果集，再 join 其他表。
   - 不要一上来 20 张表全 join。

2. **确保 join 字段有索引**
   - join 字段类型一致，避免隐式转换。
   - 小表驱动大表。

3. **只查需要的列**
   - 避免 `select *`。

4. **分步处理**
   - 用临时表、中间表。
   - 实时性不高就做宽表、物化视图、离线汇总。

5. **架构优化**
   - 分区、分表、冗余字段、缓存。

6. **看执行计划**
   - `EXPLAIN` 看每步 rows、type，避免笛卡尔积和全表扫描。

**例子：**

```sql
-- 先过滤出小结果集
select id from orders where create_time > '2024-01-01';

-- 再拿这些小结果集去 join 其他表
```

**面试速答：**  
20 张表联查优先考虑拆查询、减少 join、小表驱动大表、加索引、用临时表/宽表，而不是硬 join。

### Q3：索引的原理是什么？

**A：**  
索引本质是**排好序的数据结构**，常用 **B+ 树**。

B+ 树特点：

- 非叶子节点只存键，不存数据。
- 叶子节点存键和行指针/数据。
- 叶子节点之间用链表连接，支持范围查询和排序。
- 树矮，查询稳定，磁盘 IO 少。

常见概念：

- **聚簇索引**：叶子节点存整行数据，比如 InnoDB 主键索引。
- **二级索引 / 非聚簇索引**：叶子存主键值，查不到需要的列时要**回表**。
- **覆盖索引**：查询列都在索引里，不用回表。
- **最左前缀**：复合索引 `(a,b,c)`，`where a=1 and b=2` 能用，`where b=2` 不能用。

**例子：**

```sql
create index idx_a_b on t(a, b);

-- 能用索引
select * from t where a = 1 and b = 2;

-- 不能用索引
select * from t where b = 2;
```

**面试速答：**  
索引是 B+ 树，加快查找和范围查询；二级索引可能要回表，覆盖索引不用回表。

### Q4：如何优化 SQL 中的 `a or b` 或者 `in/not in` 等关键字性能？

**A：**

#### 1. `OR` 优化

如果 `a` 和 `b` 都有索引，数据库可能用 index merge，但经常不如 `UNION ALL`。

```sql
-- 不推荐
select * from t where a = 1 or b = 2;

-- 推荐
select * from t where a = 1
union all
select * from t where b = 2;
```

同一列多个值，用 `IN` 代替 `OR`：

```sql
-- 推荐
select * from t where a in (1, 2, 3);
```

#### 2. `IN` 优化

- `IN` 列表小且列有索引，通常没问题。
- 列表很大时，考虑临时表 join 或分批查询。
- 避免 `IN` 里放子查询。

```sql
-- 不推荐
select * from t where id in (select id from t2);
```

#### 3. `NOT IN` 优化

`NOT IN` 通常不走索引，而且遇到 `NULL` 有坑。  
推荐用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL`。

```sql
-- 不推荐
select * from t where id not in (select id from t2);

-- 推荐
select * from t
where not exists (select 1 from t2 where t2.id = t.id);
```

**面试速答：**  
`OR` 拆 `UNION ALL`，同列多值用 `IN`；`IN` 大列表用临时表；`NOT IN` 改 `NOT EXISTS`。

### Q5：什么是死锁？什么是事务？

#### 事务

**A：**  
事务是一组操作的逻辑单元，要么全成功，要么全失败。  
满足 ACID：

- **原子性**：全做或全不做。
- **一致性**：数据从一个正确状态到另一个正确状态。
- **隔离性**：事务之间互不干扰。
- **持久性**：提交后永久保存。

常用：

```sql
begin transaction;
-- 一组 SQL
commit;
-- 或 rollback;
```

#### 死锁

**A：**  
两个或多个事务互相等待对方持有的锁，形成循环等待，谁也无法继续。

**例子：**

- 事务 A 锁了行 1，等行 2。
- 事务 B 锁了行 2，等行 1。
- 互相等，死锁。

数据库通常能检测死锁，回滚其中一个事务。

**预防：**

- 按固定顺序访问资源。
- 缩短事务，减少锁范围。
- 避免大事务。
- 使用合适隔离级别。
- 加锁顺序一致。

**面试速答：**  
事务是 ACID 操作单元；死锁是互相等锁，数据库会检测并回滚一个。

### Q：什么情况下索引会失效？

**A：**  
索引失效不是绝对的，最终要看 `EXPLAIN`。但常见有以下这些情况：

---

#### 1. 索引列上做函数、运算

```sql
-- 失效：对 create_time 用了 date()
select * from orders where date(create_time) = '2024-01-01';

-- 优化：改成范围
select * from orders
where create_time >= '2024-01-01'
  and create_time < '2024-01-02';
```

```sql
-- 失效：索引列参与运算
select * from t where id + 1 = 10;

-- 优化
select * from t where id = 9;
```

---

#### 2. 隐式类型转换

```sql
-- phone 是 varchar，传了数字，可能触发隐式转换
select * from users where phone = 13800000000;

-- 优化：保持类型一致
select * from users where phone = '13800000000';
```

---

#### 3. `LIKE` 以 `%` 开头

```sql
-- 失效
select * from users where name like '%张%';

-- 可用
select * from users where name like '张%';
```

前缀模糊查询用不上 B+ 树有序性。全文搜索考虑全文索引或搜索引擎。

---

#### 4. 复合索引不满足最左前缀

索引：`idx_a_b_c(a, b, c)`

```sql
-- 能用 a
select * from t where a = 1;

-- 不能用
select * from t where b = 2;

-- 只能用 a，c 用不上
select * from t where a = 1 and c = 3;
```

---

#### 5. 范围查询后面的列失效

索引：`idx_a_b_c(a, b, c)`

```sql
-- a 能用，b 用于范围，c 用不上
select * from t
where a = 1 and b > 10 and c = 3;
```

---

#### 6. `OR` 条件中部分列没索引

```sql
-- 如果 b 没索引，可能全表扫描
select * from t where a = 1 or b = 2;

-- 优化：拆 union all
select * from t where a = 1
union all
select * from t where b = 2;
```

如果两边都有索引，可能走 `index merge`，但不一定高效。

---

#### 7. 否定条件：`!=`、`<>`、`NOT IN`、`NOT EXISTS`

```sql
-- 可能失效
select * from t where status != 1;
select * from t where id not in (select id from t2);

-- 优化：NOT IN 改 NOT EXISTS 或 LEFT JOIN ... IS NULL
select * from t
where not exists (select 1 from t2 where t2.id = t.id);
```

否定条件通常选择性差，优化器可能直接全表扫描。

---

#### 8. 排序、分组与索引顺序不一致

```sql
-- 索引是 (a, b)，这里可能 filesort
select * from t order by b, a;
```

`ORDER BY`、`GROUP BY` 的顺序、方向最好和索引一致。

---

#### 9. 返回数据比例太大，优化器放弃索引

如果 `WHERE` 条件能命中大部分行，比如 80% 以上，优化器可能觉得全表扫描更快，就不走索引了。

---

#### 10. 统计信息过期、索引选择性差

- 统计信息不准，优化器判断错误。
- 索引列重复值太多，比如性别、状态只有几个值，选择性差，可能不走索引。

---

#### 11. JOIN 字段类型、字符集、排序规则不一致

```sql
-- t1.id 是 int，t2.id 是 varchar，可能索引失效
select * from t1 join t2 on t1.id = t2.id;
```

JOIN 字段类型、字符集、排序规则最好一致。

---

#### 12. `SELECT *` 导致覆盖索引失效

如果本来可以走覆盖索引，但 `SELECT *` 要回表，成本高，优化器可能放弃索引。

```sql
-- 可能用覆盖索引
select id, name from users where name = 'Tom';

-- 回表成本高，可能不走
select * from users where name = 'Tom';
```

---

### 面试速答：

索引失效常见于：  
索引列用函数/运算、隐式类型转换、`LIKE '%xx'`、复合索引不满足最左前缀、范围查询后续列失效、`OR` 部分列无索引、`NOT IN/!=/<>`、排序分组不一致、返回数据比例大、统计信息过期、JOIN 字段类型不一致、`SELECT *` 导致回表成本高。

最终以 `EXPLAIN` 为准。
