商品页面频繁查询数据库，访问量升高后，数据库可能承受不住。把常查的商品信息放进Redis，页面就能先读取缓存，减少数据库访问。

接下来要解决的问题是：商品不存在、热门缓存过期、价格变动或Redis故障时，查询还能怎样处理。

## Redis的常见用途

Redis主要在内存中读写数据，常用于缓存、计数、去重和排行榜。不同结构适合不同数据。

| 类型 | 示例 |
| --- | --- |
| String | 商品详情、访问计数 |
| Hash | 用户姓名、等级等字段 |
| List | 按顺序保存的消息或记录 |
| Set | 不重复的用户编号 |
| Sorted Set | 按积分排序的榜单 |
| Stream | 交给消费组处理的事件 |

下面把42号商品缓存300秒：

```text
SET product:42 '{"name":"键盘","price":100}' EX 300
GET product:42
```

EX 300设置的是这个键的有效期。[Redis数据类型](https://redis.io/docs/latest/develop/data-types/)

## 缓存读取流程

数据库保存业务数据，Redis保存便于读取的副本。

```text
查询商品
    ↓
读取Redis
    ├── 有缓存 → 直接返回
    └── 没有缓存 → 查询数据库 → 缓存查询结果 → 返回
```

缓存未命中后访问数据库，通常称为“回源”。穿透、击穿和雪崩都会增加回源量，但触发原因不同。

| 问题 | 原因 | 商品场景 |
| --- | --- | --- |
| 穿透 | 请求反复查询不存在的数据 | 持续访问不存在的商品ID |
| 击穿 | 某个热门缓存失效 | 秒杀商品过期，大量请求同时回源 |
| 雪崩 | 大批缓存失效或缓存服务故障 | 很多商品同时过期，或Redis不可用 |

## 缓存穿透

999号商品不存在，Redis和数据库都查不到。如果每次都重新查询，这类请求便一直消耗数据库资源。

可以从入口和缓存两处减少重复访问：

- 检查ID格式及合理性，对异常请求限流。
- 短期缓存“不存在”的结果，例如30秒内同一ID无需再次回源。
- 使用布隆过滤器，先检查ID是否可能存在。

布隆过滤器的回答只有两类：“肯定不存在”和“可能存在”。后者可能误判，仍需继续查询。

新增商品要及时更新过滤器，否则应用可能拦住刚创建的商品。空结果缓存也可能暂时遮住新数据，需要较短TTL或在新增后清理。[Redis布隆过滤器](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

## 缓存击穿

42号商品正在秒杀。缓存到期时，很多请求同时未命中，一起涌向数据库。

可以协调同一商品的重建，让尽量少的请求承担回源：

```text
商品缓存过期
    ↓
一个请求取得重建资格 → 查数据库 → 写回缓存
其他请求短暂等待后重试，或按业务需要返回旧值
```

拿到重建资格后，要再次检查缓存，确认其他请求是否已经补齐。等待重建的请求也需要超时，避免持续堆积。

多台应用使用Redis锁时，应设置有效期和唯一标记，释放时原子核对标记，避免误删其他请求的锁。查询超过锁的有效期，仍可能产生重复重建。[缓存重建](https://redis.io/docs/latest/develop/use-cases/cache-aside/)、[Redis分布式锁](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

热门数据还可以提前刷新。业务允许短暂旧值时，也可以先返回旧缓存，再由后台更新。

## 缓存雪崩

十万条商品缓存同时写入，全部设置一小时TTL，便可能在一小时后集中失效。大量查询随之回源，数据库负载陡增。

分散TTL可以减少这种集中到期，例如设置为30分钟，再加0至5分钟随机时间。

Redis整体故障则需要另一套处理：用复制和自动切换缩短中断，同时限制回源量。必要时使用本地缓存、返回简化结果，或提示稍后重试。

恢复阶段也要控制回源速度，逐步把热门商品加载到缓存，避免重建流量再次压垮数据库。[缓存架构与流量控制](https://redis.io/blog/cache-layer-architecture-guide/)

## 数据更新后的缓存处理

价格从100元调整为80元，常见处理顺序如下：

```text
更新数据库并提交事务
    ↓
删除商品缓存
    ↓
下一次查询读到80元，再写入Redis
```

下一次读取会重新加载价格。相比直接改缓存，删除后重建可以少处理一些写入顺序问题：直接更新时，较早但执行较慢的请求，可能覆盖后来写入的新值。

提交后删除仍可能失败，查询请求也可能把旧价格晚写回缓存。可通过重试、TTL、可靠变更消息或数据库日志订阅，补做遗漏的清理。

这些措施各自覆盖不同故障环节，普通缓存仍可能短暂返回旧数据。[缓存一致性策略](https://redis.io/blog/cache-consistency-strategies/)

## 延迟双删

“双删”指两次清理缓存，业务表中的记录不会因此被删除。一种常见顺序是：

```text
第一次删除缓存
    ↓
更新数据库并提交
    ↓
间隔一段时间
    ↓
第二次删除缓存
```

第二次删除是为了解决更新期间的旧值回填。以下是一次可能发生的并发过程。

| 顺序 | 改价请求A | 查询请求B |
| --- | --- | --- |
| 1 | 清理商品缓存 | |
| 2 | | 未命中，读取到旧价100元 |
| 3 | 提交新价80元 | |
| 4 | | 将刚读取的100元写入缓存 |
| 5 | 等待后再次清理 | |

第5步清掉了B回填的旧价格，后续请求可以重新读取80元。

但延迟时长无法覆盖所有情况。B若长时间阻塞，可能在第二次清理之后才回填旧值；进程退出或网络故障，也可能让清理任务未完成。

所以，等待500毫秒不构成一致性保证。可以用可靠队列和失败重试执行延迟任务；若回源到有复制延迟的备库，还要考虑它何时才能读到新价格。

延迟双删只能缓解部分并发情形。结算等不能接受旧值的操作，仍需校验权威数据或采用相应的并发控制。

## 过期与内存淘汰

TTL决定数据何时失效，淘汰策略决定内存不足时腾出哪些空间。

| 机制 | 触发条件 |
| --- | --- |
| TTL过期 | 超过该键的有效期 |
| 内存淘汰 | 达到配置的内存上限 |

Redis会在访问时检查过期键，也会由后台周期性检查，不会为每个键各建一个定时器。

常见策略中，allkeys-lru倾向于移除近期少用的键，allkeys-lfu倾向于移除访问频率低的键。noeviction不主动清理，需要新增内存的写入会被拒绝。[Redis淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)

## RDB与AOF持久化

持久化将内存中的数据保存到磁盘，以便重启后恢复。

| 方式 | 保存内容 | 故障时可能缺少的数据 |
| --- | --- | --- |
| RDB | 某一时刻的数据快照 | 上次快照后的修改 |
| AOF | 写入操作记录 | 尚未可靠落盘的操作，取决于刷盘配置 |

AOF采用每秒刷盘时，可能丢失最近约一秒的写入。RDB和AOF可以结合使用，但自动接管仍需要另外的故障切换机制。[Redis持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

## 主从复制

复制让其他Redis节点保存主节点的数据。这些跟随节点也称副本。

```text
主节点 → 副本A
       → 副本B
```

写入通常发给主节点，副本持续接收更新。副本可用于读取，但复制滞后时会返回旧数据。

Redis复制通常是异步的。主节点已经确认成功，副本却可能尚未收到最新写入，因此故障切换时存在数据损失。副本数量增加，也不等于RPO=0。[Redis复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## Sentinel故障切换

Sentinel监控主从状态，判断故障并协调副本接管。

```text
Sentinel监控主从节点
    ↓
达到故障判断和选举条件
    ↓
选出副本作为新主节点
    ↓
客户端重新连接新主节点
```

它是监控与协调进程，不存放商品数据。官方建议稳健部署至少三个Sentinel，分布在独立的故障位置。

三个Sentinel进程与三台Redis数据节点不是同一个数量要求。两者可以共用部分机器，但职责各自独立。

应用客户端还要支持Sentinel，才能找到切换后的主节点。若固定连接旧主地址，就无法正确跟随切换。[Redis Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

## Cluster分片

数据量或写入量超出单个主节点的能力时，Redis Cluster可以将不同键分配给多个主节点。

集群有16384个哈希槽，每个键属于一个槽，每个主节点负责其中一部分。

三主三副本的布局如下：

```text
主节点A保存一部分数据 → 副本A1
主节点B保存一部分数据 → 副本B1
主节点C保存一部分数据 → 副本C1
```

各主节点存放不同部分的数据，各副本复制对应主节点。满足选举条件后，集群可以提升副本接管，由Cluster自身协调，无需Sentinel。

客户端需要支持Cluster定位键，并处理槽迁移后的重定向。复制仍然是异步的，故障切换也可能损失最新写入。[Redis Cluster规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

许多多键操作要求键位于同一槽。可以使用相同的哈希标签：

```text
cart:{42}:items
cart:{42}:total
```

两个键中的{42}使它们落在相同槽。一个键不会被自动拆分到多台机器，因此新增节点不能直接分散单个热点键的访问。

## 两种方案怎样选择

| 比较项 | 主从加Sentinel | Cluster |
| --- | --- | --- |
| 数据布局 | 一组主从保存完整数据 | 多个主节点分别保存部分数据 |
| 主要目标 | 主节点故障后的自动接管 | 分散容量和负载，同时支持接管 |
| 切换协调 | Sentinel | Cluster自身 |
| 写入扩展 | 一组主要由一个主节点处理 | 不同键可由不同主节点处理 |
| 零数据损失 | 不保证 | 不保证 |

单个主节点足以承载数据，主要需要自动接管时，可以使用主从加Sentinel。需要分散数据容量和请求负载时，再评估Cluster。
