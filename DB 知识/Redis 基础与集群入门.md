商品页面每次打开都查数据库，访问量一大，数据库就容易忙不过来。把常用的商品信息放进Redis，页面便可以先读缓存。

围绕这个场景，面试常问的事情就串起来了：查不到怎么办，缓存过期怎么办，商品改价后怎么办，Redis宕机后又怎么办。

## Redis怎么用

Redis主要在内存中读写数据。除了缓存，它也常用来做计数、去重和排行榜。

| 数据类型 | 适合保存什么 |
| --- | --- |
| String | 商品详情、访问次数 |
| Hash | 用户姓名、等级等字段 |
| List | 按顺序排列的消息或记录 |
| Set | 不重复的用户ID |
| Sorted Set | 带积分的排行榜 |
| Stream | 需要消费组处理的事件流 |

例如，把42号商品缓存五分钟：

```text
SET product:42 '{"name":"键盘","price":100}' EX 300
GET product:42
```

`EX 300`表示这个键在300秒后过期。[Redis数据类型](https://redis.io/docs/latest/develop/data-types/)

## 缓存怎么读取

商品数据保存在数据库中，Redis保存一份方便查询的副本。

```text
查询商品
    ↓
读取Redis
    ├── 有缓存 → 直接返回
    └── 没有缓存 → 查询数据库 → 缓存查询结果 → 返回
```

没有命中缓存，转而查询数据库，通常叫“回源”。缓存穿透、击穿和雪崩，都会让回源请求增多，但原因不同。

| 问题 | 发生了什么 | 商品查询的例子 |
| --- | --- | --- |
| 缓存穿透 | 总是查询不存在的数据 | 不断查询根本不存在的商品ID |
| 缓存击穿 | 一个热门键失效 | 秒杀商品的缓存突然过期 |
| 缓存雪崩 | 大量缓存同时失效或缓存服务不可用 | 大批商品同时过期，或Redis整体故障 |

## 缓存穿透

假设数据库里没有999号商品。请求先查Redis，没有；再查数据库，也没有。如果不缓存这个结果，下次还要重复查数据库。

大量这样的请求，就会穿过缓存，持续消耗数据库资源。

常见处理有三种：

- 校验参数，拦截格式错误或明显不合理的ID，并限制异常请求频率。
- 缓存“商品不存在”的标记，例如保留30秒。同一个ID再次被查询时，直接返回不存在。
- 用布隆过滤器提前筛选可能存在的ID。

布隆过滤器可以理解成一份省内存的名单检查工具。它能回答“肯定不在名单里”或“可能在名单里”，后者仍需要继续查询，因为可能误判。

这份名单需要跟着商品新增及时更新，否则新商品还没加入名单，就可能被应用拦住。缓存“不存在”的标记也有类似问题，可以通过较短的有效期和新增后的缓存清理处理。[布隆过滤器说明](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

## 缓存击穿

42号商品正在秒杀，每秒有大量访问。它的缓存一过期，很多请求同时查不到缓存，便一起去查数据库。

一种处理方式是让同一个商品在缓存重建期间，尽量只由一个请求查询数据库：

```text
商品缓存过期
    ↓
一个请求取得重建资格 → 查数据库 → 写回缓存
其他请求短暂等待后重试，或按业务需要返回旧值
```

取得重建资格后，还要再读一次缓存，因为等待期间可能已有其他请求补好了数据。等待也需要超时，不能让请求一直堆着。

如果用Redis锁协调多台应用，锁需要有过期时间和唯一标记，释放时原子检查标记，避免删掉别人的锁。锁到期而查询仍未完成时，也可能再次出现并发重建。[缓存重建说明](https://redis.io/docs/latest/develop/use-cases/cache-aside/)、[Redis锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

另一种方式是提前刷新热门缓存。允许短时间显示旧信息的场景，也可以保留旧值，由后台更新。

## 缓存雪崩

假设十万个商品在同一时间写入缓存，又都设置一小时后过期。一小时后，大量请求一起回到数据库，就可能造成雪崩。

可以把有效期分散开，例如设置成“30分钟加0到5分钟的随机时间”，减少同一时刻失效的数量。

如果原因是Redis整体不可用，随机过期时间就帮不上忙了。这时需要主从和自动切换来缩短故障时间，同时限制回源流量，必要时返回本地缓存、简化结果或提示稍后重试。

即使Redis恢复，也不要一下子把全部流量放回数据库。热门数据可以逐步预热，也就是提前加载到缓存中。[缓存失效与流量控制](https://redis.io/blog/cache-layer-architecture-guide/)

## 数据修改后怎么更新缓存

假设商品价格从100元改成80元。常见做法是：

```text
更新数据库并提交事务
    ↓
删除商品缓存
    ↓
下一次查询读到80元，再写入Redis
```

删除缓存后暂时没有值，下一次可以重新加载。直接更新缓存则需要处理多个更新请求的先后顺序：较早的请求如果执行得慢，可能把较新的缓存覆盖掉。

“先提交数据库，再删除缓存”也会遇到删除失败，或某个查询较晚写回旧价格的情况。常见补充措施是失败重试、设置有效期，或者通过可靠保存的变更消息、数据库日志订阅来补做缓存清理。它们解决的是不同环节的遗漏，普通缓存流程仍可能短暂读到旧值。[缓存一致性说明](https://redis.io/blog/cache-consistency-strategies/)

## 延迟双删

面试中说的“双删”，通常是删除两次缓存，数据库里的业务记录不会被删掉。

一种常见写法是：

```text
第一次删除缓存
    ↓
更新数据库并提交
    ↓
间隔一段时间
    ↓
第二次删除缓存
```

为什么还要删第二次？用一次改价过程来看：

| 顺序  | 改价请求A       | 查询请求B              |
| --- | ----------- | ------------------ |
| 1   | 删除商品缓存      |                    |
| 2   |             | 缓存为空，查数据库得到旧价格100元 |
| 3   | 将价格改成80元并提交 |                    |
| 4   |             | 把刚才查到的100元写回缓存     |
| 5   | 延迟后再删一次缓存   |                    |

第4步把旧价格放回了Redis。第5步就是为了清理这种晚到的旧值，让之后的请求重新查询。

延迟是想等这些查询完成，但实际耗时并不固定。如果B卡住很久，等第二次删除以后才写回100元，缓存仍然会变旧。第二次删除也可能因进程退出或网络故障而没有完成。

因此，没有一个固定的“等500毫秒”就能保证一致的答案。延迟任务可以交给可靠队列执行，并配合失败重试；如果读取的是有复制延迟的数据库备库，还需要考虑它何时能读到新价格。

延迟双删能减少一类并发问题，不能代替严格的一致性设计。结算价格等不能接受旧值的操作，需要从权威数据源校验，或使用专门的并发控制方案。

## 过期与内存淘汰

过期时间和内存淘汰是两件事：

| 机制 | 什么时候起作用 |
| --- | --- |
| TTL过期 | 键到了设定的有效期 |
| 内存淘汰 | 内存使用达到配置上限，需要腾出空间 |

过期键通常通过访问时检查和后台周期检查来清理，不是每个键都单独安排一个定时器。

常见淘汰策略中，`allkeys-lru`倾向于移除近期较少访问的键，`allkeys-lfu`倾向于移除访问频率较低的键；`noeviction`不主动淘汰，会拒绝需要更多内存的写入。[内存淘汰说明](https://redis.io/docs/latest/develop/reference/eviction/)

## RDB与AOF

Redis的数据主要在内存里，持久化用于把数据保存到磁盘，供重启后恢复。

| 方式 | 怎么保存 | 可能丢什么 |
| --- | --- | --- |
| RDB | 定期生成数据快照 | 最近一次快照之后的修改 |
| AOF | 记录写入操作 | 尚未可靠落盘的操作，取决于刷盘策略 |

AOF常用每秒刷盘方式，故障时可能丢失最近约一秒的数据。RDB与AOF可以结合使用，但持久化本身不会安排另一台Redis自动接管。[持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

## 主从复制

主从复制让另一台Redis也保存一份数据。这里把跟随主节点的节点称为副本，也就是常说的从节点。

```text
主节点 → 副本A
       → 副本B
```

应用通常向主节点写入。副本跟随主节点更新，也可以承担读取，但可能因为复制延迟读到较旧的数据。

Redis通常采用异步复制：主节点确认写入时，副本不一定已经收到。因此，主节点突然故障后，副本可能缺少最后几笔写入。增加副本数量，也不能直接承诺RPO=0。[主从复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

## Sentinel高可用

有了副本，还需要有人判断主节点是否故障，并协调副本接管。这是Sentinel负责的工作。

```text
Sentinel监控主从节点
    ↓
达到故障判断和选举条件
    ↓
选出副本作为新主节点
    ↓
客户端重新连接新主节点
```

Sentinel是监控与协调进程，不保存商品缓存。官方建议稳健部署至少使用三个Sentinel，并把它们分散到独立的故障位置。

“三个Sentinel”和“三台Redis数据节点”是两种数量。它们可以部署在部分相同的机器上，但承担的职责不同。

客户端也需要支持Sentinel，才能发现新的主节点。只把旧主节点地址写死，切换后仍可能连错地方。[Sentinel说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

## Cluster集群

如果一台主节点放不下全部数据，或者写入负载太高，就可以通过Redis Cluster把数据分给多个主节点。

Cluster使用16384个哈希槽。每个键映射到一个槽，不同主节点负责不同的槽。

常见的三主三副本部署可以这样理解：

```text
主节点A保存一部分数据 → 副本A1
主节点B保存一部分数据 → 副本B1
主节点C保存一部分数据 → 副本C1
```

三个主节点各存一部分，各自的副本保存对应部分的数据。主节点故障时，Cluster在满足选举条件后提升副本，不需要另外依靠Sentinel执行切换。

客户端必须支持Cluster，才能找到键所在的节点，并在数据迁移后处理重定向。Cluster的复制同样是异步的，切换也存在丢失最新写入的可能。[Cluster说明](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

很多多键操作要求相关键在同一个槽。例如：

```text
cart:{42}:items
cart:{42}:total
```

相同的`{42}`让这两个键映射到同一槽，方便一起操作。单个键不会自动拆到多台机器上，因此扩容并不能直接消除某一个热点键的压力。

## Sentinel与Cluster的区别

| 比较项 | 主从加Sentinel | Redis Cluster |
| --- | --- | --- |
| 数据分布 | 一个主从组保存完整的一份数据 | 多个主节点各自保存一部分 |
| 主要用途 | 主节点故障后自动接管 | 分散容量和负载，并支持故障切换 |
| 谁协调切换 | Sentinel | Cluster自身 |
| 扩大写入能力 | 单个主从组仍主要由一个主节点承担 | 可把不同键的写入分给多个主节点 |
| 是否保证零丢失 | 不保证 | 不保证 |

数据能放进一个主节点，主要关注故障接管时，可以考虑主从加Sentinel；需要把数据和请求分散到多个主节点时，再考虑Cluster。
