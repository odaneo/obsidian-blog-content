订单表的Id既用于关联数据，也可能出现在公开接口里。选型时，要考虑的不只是字段大小：编号由谁生成，多个系统怎样合并，对外如何使用，都会影响后续设计。

内部关联和公开标识可以共用一个编号，也可以分别设置。

## 自增整数

由数据库统一分配编号时，自增整数是常见选择。PostgreSQL可以使用identity列：

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);
```

bigint占8字节，主键索引和引用它的外键都比较紧凑。递增编号通常落在B-tree索引的相邻位置，有利于写入。

不过，自增不保证编号连续。回滚和序列缓存都可能留下空号。identity承担生成工作，唯一性仍要靠PRIMARY KEY或UNIQUE约束。[PostgreSQL identity列](https://www.postgresql.org/docs/current/ddl-identity-columns.html)

多个独立数据库各自从1编号，合并时可能发生冲突。可以分配不同号段，但需要额外协调。

也不能仅凭“高并发”就认定自增是瓶颈。索引页竞争、锁等待、磁盘和业务查询，都应结合真实负载排查。

## UUID

UUID是128位标识，原生存储占16字节。PostgreSQL使用uuid类型，.NET通常使用Guid。

应用可以在入库之前生成UUID，这对离线创建、多节点独立生成和跨系统合并更方便。采用合适的生成方式，碰撞概率很低，但数据库中的唯一约束仍应保留。[PostgreSQL UUID类型](https://www.postgresql.org/docs/current/datatype-uuid.html)

代价主要在空间和索引维护。相比bigint，UUID索引通常更大；随机的UUIDv4可能让插入分散到多个索引页，增加写入成本。具体查询和写入速度，仍取决于索引、数据规模与访问方式。

UUIDv7包含时间顺序特征，有助于改善新增记录的索引位置。它也会透露一定的时间信息，生成函数能否使用，需要看实际版本。

## 公开编号与访问权限

自增编号容易被枚举，随机UUID较难猜到。但订单编号再随机，接口也必须验证它是否属于当前用户或租户。

编号回答“查哪条记录”，权限回答“谁能查看”。两者不能互相替代。[OWASP对象访问控制](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)

## 内部与外部各用一列

内部关联很多，又希望公开接口使用独立编号时，可以组合两种方式：

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL UNIQUE,
    title text NOT NULL
);
```

应用创建订单时提供public_id。订单明细等表引用整数id，对外接口则接收和查询public_id。

主键仍只有id。public_id拥有独立的唯一约束，并未与id组成复合主键。

这样能保留紧凑的内部关联，但要多维护一个UUID唯一索引。合并系统时，内部整数编号仍可能需要重新映射，公开UUID无法自动解决这一步。

## 主键与聚集索引

在SQL Server中，主键约束和聚集索引可以分别配置。理解概念后，还要按数据库选择对应语法。[SQL Server聚集索引](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-clustered-indexes?view=sql-server-ver17)

PostgreSQL的主键会建立唯一索引，但表数据不会因此持续按主键顺序排列。CLUSTER可以按某个索引重排数据，之后的写入却不会自动维持这个排列。[PostgreSQL CLUSTER](https://www.postgresql.org/docs/current/sql-cluster.html)

比较性能时，应一起看数据库存储方式、索引结构和UUID生成规则。只比较“数字”与“字符串”，不足以判断实际成本。

## 按需求选型

| 需求 | 候选方案 |
| --- | --- |
| 单库生成编号，内部关联较多 | 自增bigint |
| 多节点独立生成，需要合并数据 | UUID或专门设计的分布式编号 |
| 内部关联紧凑，对外编号独立 | bigint主键加UUID唯一列 |
| 写入性能要求较高 | 按实际索引和数据规模测试 |

大批量导入还涉及工具、事务批次和索引维护。暂时移除约束或延后建索引，需要配套的导入安排，不能直接推广到所有生产表。
