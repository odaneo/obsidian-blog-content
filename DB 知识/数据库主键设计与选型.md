给订单加一个Id，看起来只是选一种字段类型。等系统需要批量导入、开放对外接口，或者合并多个系统的数据时，主键选型的影响就会显现出来。

主键设计涉及两件事：数据库内部如何关联记录，对外又如何标识记录。两者可以使用同一个编号，也可以分开设计。

## 自增整数适合集中生成编号

自增列让数据库为新记录分配整数编号。在PostgreSQL中，可以使用identity列：

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
);
```

bigint占用8字节，作为主键和外键都比较节省空间。递增的编号通常会写入B-tree索引中相近的位置，对写入性能也有帮助。

自增编号不一定连续，事务回滚、序列缓存等都可能让编号出现跳号。identity负责生成编号，是否唯一仍由PRIMARY KEY或UNIQUE约束保证。[PostgreSQL identity 列](https://www.postgresql.org/docs/current/ddl-identity-columns.html)

如果多个独立数据库都从1开始编号，合并数据时就可能出现重复编号。分配不同号段等方式可以解决这个问题，但也会增加协调工作。

自增编号也不一定是高并发下的性能瓶颈。限制可能来自索引页、锁、磁盘或其他业务查询，需要结合实际负载排查。

## UUID支持独立生成编号

UUID是一种128位标识，使用原生类型存储时占16字节。它在PostgreSQL中对应uuid类型，在.NET中通常用Guid表示。

应用不必等到写入数据库时才生成UUID，因此更方便支持离线创建、多节点写入和跨系统数据合并。合理的生成方式可以让重复的概率极低，数据库中仍需保留唯一约束。[PostgreSQL UUID 类型](https://www.postgresql.org/docs/current/datatype-uuid.html)

UUID索引通常比bigint索引占用更多空间。UUIDv4这类随机编号，还可能把新增记录分散到不同的索引页，增加写入成本。不过，这不意味着UUID查询一定很慢，索引设计和实际负载同样影响性能。

UUIDv7带有时间顺序特征，也是可以考虑的选择。它有助于让新增记录落在相近的索引位置，但编号中会包含时间信息，生成函数是否可用也取决于所用版本。

## 编号难猜不等于安全

自增编号容易被逐个猜出，随机UUID通常更难猜。无论采用哪种编号，查询订单时都需要确认订单是否属于当前用户或租户。

外部传来的UUID即使看起来很随机，也仍需校验访问权限。编号用来识别记录，权限则决定谁可以访问。[OWASP 对对象访问控制的说明](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)

## 内部用整数对外用UUID

如果内部表之间的关联较多，对外又想使用独立编号，可以同时保留两列：

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id uuid NOT NULL UNIQUE,
    title text NOT NULL
);
```

新增订单时，由应用提供public_id。订单明细等内部表通过id关联订单，对外接口则使用public_id查询。

这里的主键只有整数id，public_id是另一个具有唯一约束的公开编号，两者没有组成复合主键。

这种设计让内部关联字段保持紧凑，代价是多维护一个UUID唯一索引。跨系统合并数据时，仍可能需要重新对应内部整数编号，增加UUID列并不能省去这一步。

## 主键不等于聚集索引

在SQL Server中，主键约束与聚集索引是两个概念，可以分别配置。相关语法并不适合直接套用到PostgreSQL。[SQL Server 聚集索引](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-clustered-indexes?view=sql-server-ver17)

PostgreSQL会在创建主键时建立唯一索引，但不会让表中的数据始终按主键顺序存放。CLUSTER可以按照索引顺序重新整理表数据，不过后续写入不会自动维持这个顺序。[PostgreSQL CLUSTER 说明](https://www.postgresql.org/docs/current/sql-cluster.html)

比较插入性能时，数据库类型、索引结构和UUID生成方式都需要纳入考虑，只看“数字还是字符串”并不够。

## 结合需求选择主键

| 主要需求 | 可以考虑的方案 |
| --- | --- |
| 单库集中写入，内部关联为主 | 自增 bigint |
| 多节点独立生成编号、需要合并数据 | UUID 或经过设计的分布式编号 |
| 内部紧凑关联，对外使用独立编号 | bigint 主键加 UUID 唯一列 |
| 对写入性能特别敏感 | 用真实索引和数据量测试候选方案 |

批量导入大量数据时，还需要考虑导入工具、事务如何分批，以及维护索引的成本。移除约束或推迟创建索引，需要有专门设计的导入流程配合，并不适用于所有生产表。
