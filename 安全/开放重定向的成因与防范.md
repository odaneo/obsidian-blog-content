用户打开熟悉的网站，输入账号密码，登录成功后，眼前却又出现一张登录表单。页面样式几乎没变，他以为刚才没有登录成功，于是再输了一遍。

第二次提交，可能已经落到了另一个人的服务器上。

开放重定向常常藏在这样的衔接处。它借用网站已有的信任，把用户带向一个未经允许的地址。而在代码里，问题可能只有一行。

## 一、跳转地址由谁决定

登录前记下用户想访问的页面，登录后再送他回去，是很常见的功能。这个目标通常保存在 `returnUrl` 一类参数中：

```text
/Login?returnUrl=/orders
```

正常情况下，用户完成登录后会回到订单页。

但参数可以被修改。如果应用直接使用传入的地址，没有校验，或者校验规则存在缺口，攻击者就可能把目标换成外部站点。这便形成了开放重定向漏洞。

下面的代码只展示登录成功后的跳转分支，省略身份验证等逻辑：

```csharp
[HttpPost]
public IActionResult Login(string returnUrl)
{
    // 此处省略身份验证，假设登录已经成功。
    return Redirect(returnUrl);
}
```

`Redirect` 按参数生成重定向响应，并不会替业务判断这个目的地是否可信。应用把选择去向的权力，交给了请求中的输入。

## 二、可信链接如何成为跳板

以两个示例域名说明：`trusted.example` 代表正常网站，`phishing.example` 代表攻击者控制的页面。

攻击者可以构造如下入口：

```text
https://trusted.example/Login?returnUrl=https%3A%2F%2Fphishing.example%2Ffake-login
```

如果登录页把这个参数保留到表单提交中，而登录成功后的处理又没有检查它，就可能出现这样的过程：

1. 用户看到入口属于熟悉的网站，打开了链接。
2. 用户在真实网站完成登录。
3. 网站根据被篡改的参数，将浏览器带到外部页面。
4. 外部页面仿照原站的样式，诱导用户再次提交凭证。

这里有一个容易忽略的前提：打开链接通常发起 GET 请求，而前面的示例处理 POST 请求。攻击链还依赖登录流程把恶意参数传到最终的跳转分支，单击链接本身并不会直接执行那个 POST 方法。

浏览器跳到外部页面后，地址栏会发生变化。风险在于用户可能没有留意变化，仍把刚才对真实网站的信任带到了新页面。

这类钓鱼链路也是微软文档列举的典型场景。[开放重定向攻击示例](https://learn.microsoft.com/en-us/aspnet/core/security/preventing-open-redirects?view=aspnetcore-10.0#an-example-attack)

## 三、重定向发生时，页面会怎样

后端返回 302 响应，并通过 `Location` 指定新的地址。浏览器接下来如何处理，还要看最初发起的是什么请求。

| 请求方式 | 收到重定向后的行为 | 当前页面是否更换 |
| --- | --- | --- |
| 当前窗口中的普通链接、表单提交、`window.location` 导航 | 浏览器通常继续导航到目标地址 | 会 |
| `fetch` 或 XHR 后台请求 | 在后台按相应规则处理重定向 | 不会自动更换 |

对于整页表单提交，流程通常是：

```text
用户提交表单
→ 浏览器发送请求
→ 服务端返回 302 和 Location
→ 浏览器导航到新地址
```

对于 `fetch`，重定向属于后台请求的处理过程：

```javascript
const response = await fetch("/redirect-endpoint", {
    redirect: "follow"
});

// 请求成功时可得到响应，但这段代码不会让当前页面导航。
```

`follow` 是 fetch 默认的重定向模式。不过，“跟随”并不保证 JavaScript 一定能读到目标响应；跨域时仍受 CORS 等规则限制，也可能以错误结束。[Fetch 重定向配置](https://developer.mozilla.org/en-US/docs/Web/API/RequestInit#redirect)

因此，不能因为地址栏没有变化，就认定后端重定向没有发生。后台请求可以发生重定向，页面导航则是另一件事。

如果前端随后把未经验证的地址赋给 `window.location`，仍可能把用户带到外部站点。是否存在风险，要沿着实际请求和导航流程判断，不能仅凭“这里用了 fetch”下结论。

## 四、危险来自信任的延续

开放重定向让攻击者有机会把可信站点当作入口，将访问者引向钓鱼页、欺诈内容或恶意下载页面。

但跳转本身并不等于凭证已经失窃。前面的例子还需要用户在伪造页面再次输入信息。攻击能否得逞，与页面伪装、提示内容和用户操作等因素有关，不能笼统断言成功率。

我们能够在应用中控制的，是跳转目的地。一个经过自己网站的链接，不应因此获得前往任意地址的许可。

## 五、把跳转限制在允许的范围内

### 1. 站内跳转使用框架校验

如果业务只需要登录后返回站内页面，就应明确只接受站内路径。

ASP.NET Core MVC 提供了 `LocalRedirect`：

```csharp
return LocalRedirect(returnUrl);
```

它会在执行重定向时检查地址，非本地 URL 会引发异常。为了让缺失或不合法的输入得到明确处理，可以先用 `Url.IsLocalUrl` 判断，再回退到固定页面：

```csharp
private IActionResult RedirectAfterLogin(string? returnUrl)
{
    if (!string.IsNullOrEmpty(returnUrl)
        && Url.IsLocalUrl(returnUrl))
    {
        return LocalRedirect(returnUrl);
    }

    return RedirectToAction("Index", "Home");
}
```

这里的“本地”是框架定义的 URL 形式，例如 `/orders` 和 `~/orders`。即使完整 URL 的域名与本站相同，也不能直接当作 `IsLocalUrl` 接受的本地地址。[本地跳转与地址校验](https://learn.microsoft.com/en-us/aspnet/core/security/preventing-open-redirects?view=aspnetcore-10.0#localredirect)

### 2. 外部跳转使用明确的允许列表

如果确实需要跳转到合作站点，就要检查解析后的地址组成，而不是只看字符串中是否出现某个域名。

下面的 MVC 示例仅允许两个指定主机，并限制为 HTTPS、443 端口和不含用户信息的 URL：

```csharp
private IActionResult RedirectToPartner(string? returnUrl)
{
    if (!Uri.TryCreate(returnUrl, UriKind.Absolute, out var uri))
    {
        return BadRequest("跳转地址格式不正确");
    }

    var allowedHosts = new HashSet<string>(
        StringComparer.OrdinalIgnoreCase)
    {
        "partner.example",
        "app.partner.example"
    };

    if (uri.Scheme != Uri.UriSchemeHttps
        || uri.Port != 443
        || !string.IsNullOrEmpty(uri.UserInfo)
        || !allowedHosts.Contains(uri.IdnHost))
    {
        return BadRequest("不允许跳转到该地址");
    }

    return Redirect(uri.AbsoluteUri);
}
```

这段策略允许指定主机上的所有路径。如果业务只允许进入某个固定页面，还应收紧路径和查询参数，或直接由服务端保存完整目标地址。

允许列表中的站点也应可信。如果目标页面本身又能跳转到任意地址，前一道主机检查仍可能被绕着走。

### 3. 相对路径仍然需要验证

用 `/orders/detail` 代替完整 URL，可以减少输入范围，但约定本身不会拦住恶意请求。

尤其不能只检查地址是否以 `/` 开头。`//phishing.example` 这样的地址带有主机部分，并不是站内路径。应交给 `Url.IsLocalUrl` 判断，而不是自己拼凑字符串规则。

当可选页面很少时，还可以只接收 `orders`、`profile` 这样的标识，由服务端映射到固定路由。用户选择目的地的名称，实际地址由应用决定。

一次跳转只发生在很短的瞬间，却会把用户带进下一段流程。把这个去向校验清楚，才能让用户对当前网站的信任，有一个可靠的落点。
